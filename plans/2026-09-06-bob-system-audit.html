Overview

Bob turns approved work into execution and reviewable changes. OODA owns deliberation, conversations, research and provenance. Shared infrastructure supports both. The recommended architecture keeps those product boundaries while making authorization, persistence and terminal outcomes consistent across transports.

The highest-value change is to make every accepted command recoverable and every user-visible status traceable to durable evidence. Framework consolidation is secondary. A package boundary alone cannot guarantee that a stop was honored, an event survived restart, or a proposal is still valid.

Goals & Non-goals

Goals: authorized resource access at the domain boundary; recoverable admission and execution; isolated workspace mutation; branch-correct conversation context; typed research results; tested browser/desktop transport continuity; release gates based on complete evidence.

Non-goals: a monorepo rewrite, forced migration of all tRPC to Effect RPC, retirement of the two documented daemon deployment shapes, replacement of ForgeGraph ownership, new offline product scope, or a claim of production/device acceptance from source review.

1. Domain authorization is the first mutation boundary

Each public command resolves a principal, tenant/workspace and resource. Domain services authorize access before reading protected data, decrypting secrets, subscribing to host events or creating external effects. Transports translate requests and errors; they do not define divergent permission rules. Host filesystem and process access require an explicit runner capability with bounded roots and operations. A trusted local operator is an explicit mode, not an accidental consequence of signing in.

2. Accepted work has a durable state machine

Prepare immutable host context before publishing queued admission. Queued work is claimable only when its required context is present; historical rows missing context require exact replay. Admission records the idempotency key and immutable input digest. Execution proceeds through queued, claimed/running and terminal states, with explicit stopping and recovery states. Every claim increments an attempt/fencing token; all heartbeat and terminal writes must match it. Expired owners cannot overwrite newer attempts. Cancellation is requested, delivered, and confirmed by process exit; these facts must remain distinct.

3. Reliable events precede realtime delivery

Persist producer frames to a bounded journal before sending. The gateway deduplicates by producer/session/attempt/sequence and acknowledges only after the database commit. Broadcast follows persistence. Reconnect replays unacknowledged frames and subscribers resume from a durable cursor. The gateway awaits transactional persistence directly; the former in-memory batch writer is removed. Producers retain journaled frames until durable acknowledgement. Shutdown waits for outstanding work within a bounded deadline; incomplete delivery remains recoverable in the producer journal instead of being reported as success.

4. Each execution owns a workspace

Create an isolated checkout for each execution, recording base revision, branch/bookmark, ownership and retention policy. Validate setup before launch. Preserve user dirt and partial outputs. Retain the existing server Node daemon and bundled Go daemon deployment distinction. They must pass a common protocol conformance fixture for claim, stop, replay, acknowledgment and terminal outcomes. Any additional task-runner daemon must be declared in the runtime inventory with its supported protocol.

5. Conversations are governed by canonical visible history

Store the selected branch, visible event watermark, context-pack digest and provider identity for every host turn. Start fresh with the full canonical transcript as the safe initial behavior. Permit native resume only after confirming that its durable artifacts and exact history prefix exist. Forked or edited histories must never resume unrelated later context. Keep provider session retention separate from disposable credentials and scratch files.

6. Cross-product action remains proposal driven

OODA proposals carry immutable payload digest, owner, version, consequence, rollback and expiry. Server time under the transaction lock decides whether a new approval remains valid. The same transaction creates the approval receipt and delivery outbox. Delivery uses a stable idempotency key and persists the external receipt before projecting completion. Reconciliation eligibility must be applied before bounded selection so excluded work cannot starve eligible work.

7. Research contracts separate identity from results

Persist exploration identity, vault and input independently of replaceable progress/results. A versioned result schema includes visited sources, graph counts, complete cluster summaries, partial errors and terminal timestamps. The Python writer and TypeScript/API reader validate the same golden fixtures. Historical records without enough provenance are marked unresolved; migration must never invent a vault.

8. Client success follows durable receipts

Web, phone and desktop render accepted, queued, running, stopping, blocked, failed and completed states from the same contracts. Optimistic updates must reconcile or roll back. Desktop startup covers bootstrap authentication, subsequent assets/API calls, actual WebSocket handshake, daemon readiness and shutdown as one integration flow. Mobile offline delivery is a separate opt-in capability requiring account-scoped durability and deduplication.

9. Release evidence is scoped and complete

For each deployable target, derive the dependency closure and expected tasks from the same SHA. Require all necessary phases and trustworthy terminal records, including cache provenance. Unknown evidence blocks release. Match supported Node/runtime versions. Apply schema changes before dependent code, with additive expand/contract migration and restore rehearsals. Verify running revision and a signed-in product flow after deployment; retain independent native device and provider acceptance gates.
