Bob SDLC: close the loop from run to production Accepted

2026-11-15 · gmackie/bob (coordinator, sdlc-view, edge, TUI) + t3code (publish step) · follows BOB-75

Recommendation: Teach the coordinator the second half of its own state machine. T3 pushes the agent's branch when a run succeeds. The coordinator then opens the PR, follows ForgeGraph CI, approves on green, merges per policy, and watches the deploy until it records production evidence. Today every successful item stops in Validating because none of those steps exist.

Proposed flow

running→ T3 pushes branch → validating
PR open · CI on head→ CI green → review
approve · merge→ merged → deploying
deploy · health→ evidence → completed

Each step is a coordinator operation with a durable receipt and an actor, so web, mobile, the TUI and the plugin get the same buttons for free. Milestones review-ready, merged and production-verified are written along the way, which also unblocks plan dependencies. The coordinator writes Kanbanger state: In Review when the PR opens, Done only after production evidence.

Decided 2026-11-15: T3 publishes (pushes the branch and opens the PR); merge and deploy run automatically on green CI through a per-plan autoMerge whose default is the policy's release.autoMergeDefault, on in production. Tracked in BOB-82 and T3CODE-114.

Decision 1: who publishes the branch

A. T3 publishes on success Recommended

  • The T3 environment commits the worktree, pushes bob/<ISSUE>-<slug>, and adds the pushed head to the receipt
  • Deterministic; the only place that holds the work and has git credentials
  • Costs a t3code PR and an optional receipt field

B. The agent pushes; the coordinator verifies

  • The item instructions tell the agent to push; the coordinator reads the branch head from Forgejo
  • No t3code change
  • Relies on the model following instructions; a missed push stalls silently

C. The coordinator pushes the bundle

  • Fetch T3's evidence bundle and push from hetzner-bob
  • Needs a bundle-transfer API and git credentials on the coordinator
  • Most moving parts

Decision 2: how far it runs without you

Per plan, default: auto to merge Recommended

  • Open PR and approve on green at the exact head: automatic (matches your CLAUDE.md rule)
  • Merge: automatic when the plan sets autoMerge, otherwise a tier-2 confirm in any surface
  • Deploy follows the repo's own merge-to-deploy; promote and rollback stay tier-3 typed confirm

Always confirm merges

  • Every merge waits for a tier-2 confirm
  • Safest; a pile of items waits on you in the Attention tab

Fully automatic

  • Merge on green with no confirm, as the legacy auto-merge did
  • Fastest; no human sees the PR before production

Scope

Goals

  • Every item can reach completed with real PR, CI, merge and deploy evidence
  • Release and deploy actions on web, TUI, mobile and plugin, with tiers
  • Milestone dependencies work for review-ready, merged and production
  • BOB-80's CI detail shows the real PR head

Non-goals

  • Retiring the legacy auto-drain and auto-merge loops (separate track)
  • Running checks inside T3 (validation = ForgeGraph CI on the pushed head)
  • Enabling budget enforcement (still shadow until ~2026-11-22)

Risks

High An auto-merge ships a bad change. Merge only on green CI at the exact head with an approval at that head; merge is opt-in per plan; rollback is one tier-3 command.

Medium The legacy auto-merge and the coordinator both act on the same PR. The coordinator only touches PRs it opened (recorded in its release table); legacy loops ignore bob/ branches it owns.

Medium The t3code change is in another repo with its own owner. The receipt field is optional, so Bob can ship first and fall back to reading the branch head from Forgejo (option B) until T3 releases.
