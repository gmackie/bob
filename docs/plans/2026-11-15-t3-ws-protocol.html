0. Verdict

  • A plain Node client is feasible. The transport is RpcSerialization.layerJson: one JSON object (or array of objects) per WebSocket text frame. The envelope has six message tags. The one thing a client must not miss is that the server waits for an Ack after every Chunk of a stream before it sends the next one.
  • Auth: send the same Authorization: Bearer <authToken> header on the upgrade request. The WS upgrade falls back to the same credential check the HTTP routes use. You can also mint a one-time wsTicket over HTTP and pass it in the query.
  • No HTTP route exists for dispatchCommand or runtime-request.respond, so answering a question requires the socket (or the MCP endpoint, which needs a different credential). Read-only thread and shell snapshots do have HTTP routes.

1. Endpoint and authentication

1.1 URL

GET {baseUrl with http→ws, https→wss}/ws?orchestrationProtocol=2
Upgrade: websocket
Authorization: Bearer <authToken>
  • The route is HttpRouter.add("GET", "/ws", …). apps/server/src/ws.ts:3764-3766 (deployed: 3600-3602)
  • The query parameter orchestrationProtocol=2 is required. Without it the server returns HTTP 426 with {"code":"orchestration_protocol_incompatible",…} and does not upgrade. ws.ts:3769-3779, ws.ts:804-809; constants packages/contracts/src/environment.ts:13-16 (ORCHESTRATION_PROTOCOL_VERSION = 2, param orchestrationProtocol)
  • Leave out frameParts. With it, the server splits frames larger than 48 KiB into parts prefixed with \u001e. Without it, every frame arrives whole. ws.ts:3877-3889; packages/shared/src/socketFrameParts.ts:6-17
  • Optional telemetry query parameters (clientSurface, clientAppVersion, …) are read only for analytics. ws.ts:823-865

1.2 Credential resolution on upgrade

authenticateWebSocketUpgrade(request, "rpc") apps/server/src/auth/EnvironmentAuth.ts:1470-1527 checks two things in order:

  1. ?wsTicket=<ticket> in the query, if present. This is a one-time token from POST /api/auth/websocket-ticket/rpc. If the session is DPoP-bound, the request also needs a dpop header or query proof. EnvironmentAuth.ts:1476-1523; contracts/src/environmentHttp.ts:616-629; auth.ts:241-256
  2. Otherwise authenticateRequest(request), the same function the HTTP middleware uses EnvironmentAuth.ts:1525; auth/http.ts:231-240. It takes, in order, a session cookie, then Authorization: Bearer <token>, then Authorization: DPoP <token>. EnvironmentAuth.ts:697-741 (parseBearerToken, selectRequestCredential), 839-875. The Origin check applies only to cookie credentials, so a Node client that sends no Origin header passes. EnvironmentAuth.ts:753-760, 839-856

Sessions with the MCP client subject are rejected everywhere except /mcp EnvironmentAuth.ts:677-684. A token that is DPoP-bound (has a proofKeyThumbprint) needs DPoP proofs, which a plain client cannot easily produce EnvironmentAuth.ts:858-875.

2. Wire format (Effect RPC over WebSocket, JSON)

2.1 Serialization

  • The server wires up RpcServer.makeProtocolWithHttpEffectWebsocket with RpcSerialization.layerJson. ws.ts:3798-3837
  • json serialization: decoding is JSON.parse(frame), and an array is treated as several messages. Encoding is JSON.stringify(message) with one message per frame. It is not ndjson, msgpack or JSON-RPC. effect/src/rpc/RpcSerialization.ts:141-152, 635
  • Payloads and results are encoded with Schema.toCodecJson. DateTimeUtc becomes an ISO-8601 string, branded IDs become plain strings, and optional keys are omitted. RpcSerialization.ts:41
  • Unions in t3 contracts are discriminated by plain fields: kind (stream items), type (events, commands, turn items). Only RPC envelopes and tagged errors use _tag.

2.4 Flow control (required)

The socket protocol reports supportsAck: true effect/src/rpc/RpcServer.ts:1855-1866. For each request, streamEffect writes one Chunk, then closes a latch and waits on it. Only an Ack carrying that requestId reopens the latch. RpcServer.ts:457-511, 219-222

  • Deployed: only terminal streams have an ack window. subscribeThread and subscribeShell stall after the first Chunk until it is Acked. [deployed] apps/server/src/terminal/OutputProtocol.ts:15-40 (withTerminalOutputWindow)
  • HEAD: withOutputWindow sends up to 8 Chunks for subscribeShell, subscribeThread and subscribeServerConfig before it waits. OutputProtocol.ts:14-31, 69-136
  • Client rule for both versions: send {"_tag":"Ack","requestId":id} immediately after each Chunk, once per Chunk.

2.5 Keepalive and lifecycle

  • Effect's client pings every 5 s and treats the connection as dead if no frame arrives within the timeout effect/src/rpc/RpcClient.ts:1275, 1431-1460. The server answers Ping with Pong RpcServer.ts:1023-1025. Ping every 10–15 s and reconnect after 30 s without any frame.
  • Sending to an unknown requestId (an Ack or Interrupt after Exit) is a no-op. An unknown _tag produces a Defect. RpcServer.ts:208-244
  • The server ends the socket when the session is revoked. ws.ts:3890-3903 (sessions.awaitInvalidation)
  • Requests on one socket run concurrently (concurrency is unbounded). You can multiplex one subscribeShell, several subscribeThread streams and unary dispatchCommand calls by id.

4. Resume semantics

Thread stream ws.ts:917-1148 (deployed 825-…)

  • Cursor: the highest sequence from event items, or snapshotSequence from a snapshot item.
  • Without afterSequence, the stream sends snapshot, then synchronized (if requested), then live events after snapshotSequence. ws.ts:1001-1041
  • With afterSequence, the server replays events after the cursor up to the high-water mark, then sends synchronized, then live events. It sends a full snapshot instead when any of these hold: the cursor is above the high-water mark, the cursor is in pruned history, the replay is longer than THREAD_RESUME_MAX_REPLAY_EVENTS or too many bytes, the thread was recreated, or decideThreadResume picks snapshot. ws.ts:1045-1145
  • The server subscribes before reading stored events, so the client must drop events whose sequence ≤ its cursor to dedupe the overlap. ws.ts:1044
  • A snapshot item always replaces local thread state, even in the middle of a resume.
  • Live *.updated events may be coalesced, so only the latest version of an entity is guaranteed. ws.ts:949-962 (coalesceThreadLiveStream)

Shell stream ws.ts:1150-… (deployed 1062-1340)

  • Cursor: the highest sequence from thread.* or project.* items, or snapshot.snapshotSequence from an authoritative snapshot (one without resolvedRepositoryIdentityRoots).
  • With afterSequence, the server sends a full snapshot if the gap is negative, larger than SHELL_RESUME_MAX_GAP, or pruned. Otherwise it sends enrichment-only snapshot items, then the replayed thread.updated/thread.removed items, then synchronized, then live items.
  • snapshot-required (HEAD only) is sent only if you asked for httpSnapshotFallback. In that case, load GET /api/orchestration/shell and subscribe again from its snapshotSequence.

synchronized

Emitted once, only when requestCompletionMarker:true. It marks that the initial snapshot or replay has been delivered and live events follow. ws.ts:996-999

5. Minimal client sketch

import WebSocket from 'ws';
export function connectT3({ baseUrl, authToken }) {
  const url = new URL('/ws', baseUrl); url.protocol = url.protocol === 'https:' ? 'wss:' : 'ws:';
  url.searchParams.set('orchestrationProtocol', '2');
  const ws = new WebSocket(url, { headers: { Authorization: `Bearer ${authToken}` } });
  let nextId = 1; const pending = new Map(); // id -> { onChunk?, resolve, reject }
  const send = (m) => ws.send(JSON.stringify(m));
  ws.on('message', (data) => {
    const msgs = [].concat(JSON.parse(String(data)));
    for (const m of msgs) {
      if (m._tag === 'Chunk') { send({ _tag: 'Ack', requestId: m.requestId }); pending.get(m.requestId)?.onChunk?.(m.values); }
      else if (m._tag === 'Exit') { const p = pending.get(m.requestId); pending.delete(m.requestId);
        m.exit._tag === 'Success' ? p?.resolve(m.exit.value) : p?.reject(m.exit.cause); }
      else if (m._tag === 'Defect') { for (const p of pending.values()) p.reject(m.defect); pending.clear(); }
    }
  });
  const ping = setInterval(() => ws.readyState === 1 && send({ _tag: 'Ping' }), 10_000);
  ws.on('close', () => clearInterval(ping));
  const call = (tag, payload) => new Promise((resolve, reject) => {
    const id = nextId++; pending.set(id, { resolve, reject }); send({ _tag: 'Request', id, tag, payload, headers: [] }); });
  const stream = (tag, payload, onChunk) => { const id = nextId++;
    const done = new Promise((resolve, reject) => pending.set(id, { onChunk, resolve, reject }));
    send({ _tag: 'Request', id, tag, payload, headers: [] });
    return { done, cancel: () => send({ _tag: 'Interrupt', requestId: id }) }; };
  return { ws, call, stream };
}

6. Risks and open points

  • Version drift. HEAD adds windowed acks, snapshot-required, userOnly and phase. These are all additive, and a client that Acks every Chunk and ignores unknown fields works on both versions. Effect's RpcMessage is identical in 4.1.2 and 4.1.3.
  • Proxy. Make sure the hetzner-bob front proxy forwards Upgrade and Authorization on /ws; if not, use the wsTicket flow. This was not tested live.
  • Snapshot size. Without acceptBoundedSnapshot, a long thread's snapshot can be several MB in one frame. That fits within ws's 100 MiB default maxPayload, but it is slow.
  • Who answers. Do not auto-answer when userOnly is set (HEAD) or when responseCapability.type is not_resumable. The MCP tool also refuses to approve permission requests through the answers path. mcp/toolkits/thread/tools.ts:131
