Agent Credential Management in the UI Approved

2026-08-29 repo gmacko/bob priority P1 supersedes TODOS.md §3

Bob can detect a dead agent but has never been able to fix one. This design adds the missing write path — browser-driven re-authentication over the channel the daemon already holds — plus the one status the health model was missing, and a circuit breaker that stops the backlog burning while nobody is watching.

01Overview

On 2026-08-29 all three agents on the primary agent host were down simultaneously: claude with an expired OAuth session, codex with a revoked token, and grok reporting healthy while dying on every run with 402 Payment Required. With zero healthy agents the task runner degraded to “keep the configured one”, then spent eight days claiming work, failing in about a second, posting “produced no changes”, and resetting issues to unstarted every 120 seconds across the entire backlog.

The only remedy was SSH to the host and a hand-run auth script. This design removes that requirement entirely: state and remediation both live in the UI.

Two findings reshaped the original TODO. First, the read path already exists end-to-end — probeCliProvider → collectHostSnapshot → relay → dashboard — so this is not a new health surface, it is a missing write path plus one missing status. Second, the execution daemon already runs as the same Unix user that owns the credential files, with ProtectHome=false and write access to that home directory. The TODO's scariest caveat — “a UI-triggered auth has to land there as the right user, not as the web process” — is already solved by the existing process topology. Nothing new needs privileges.

Goals

  • Re-authenticate any agent on any node from the browser. No SSH, ever.
  • Report state truthfully, including authenticated-but-out-of-credit.
  • Distinguish “sign in” from “top up” so operators cannot loop on the wrong remedy.
  • Stop dispatch on confirmed-dead agents instead of burning the backlog.

Non-goals

  • Rendering, storing, or proxying any provider token.
  • Role-based access control — Bob has no user roles and does not need them yet.
  • Writing credential files ourselves. The vendor CLI owns its own storage.
  • Replacing the starvation alerting that already exists.

02Architecture

Everything rides the WebSocket connection the execution daemon already holds to the gateway. No new listener, no new secret, no new process, no new dependency — node-pty is already a direct dependency of the daemon.

Read path — exists, needs enrichment

The pipeline is live today: probeCliProvider (apps/bob-execution/src/providers/cli-provider.ts:44) → collectHostSnapshot (apps/bob-execution/src/daemon/index.ts:224) → hello/heartbeat → relay broadcast (apps/bob-ws-gateway/src/relay.ts:2562) → provider-capacity-cards.tsx:180. Three changes:

  1. Extend the deployed enum with no_credit, rather than adopting the TODO's proposed fourth vocabulary. ProviderHealthWire is already consumed in three places, and its existing unauthenticated / unavailable already mean what the TODO called expired / unknown.
  2. Add detail?: string carrying the provider's verbatim error. The 402 body named the exact problem; that string is what distinguishes “top up” from “sign in”.
  3. Fix the grok probe. cli-provider.ts:21 probes grok with ["models"], which exits 0 on valid-but-exhausted credentials. This single line is why the agent reported healthy for eight days.

No probe can detect a 402. Balance is not an auth fact. The only thing that ever knew the truth was the exit code of a real dispatch — the signal assessAgentHealth already consumes and the UI currently ignores. So no_credit is latched from run outcomes, not probed, and it clears only on a subsequent successful run — never on a successful re-auth, because re-authenticating does not buy credit.

The key security property. We never write a credential file. The daemon spawns the vendor CLI under a PTY and the CLI writes its own credentials, as the same user, to the same home directory it uses when run over SSH today. We only relay a URL outward and a short-lived code back. There is no point in the flow where Bob holds a token, so there is no token Bob can leak.

03Pending-auth lifecycle

The daemon holds Map<requestId, { provider, pty, startedAt, phase }> in memory only. A device code has no business in Postgres. One pending auth per provider; a second Start for a live provider is rejected rather than spawning a second PTY.

  • Phases: spawning → awaiting_url → awaiting_code → verifying → done | failed.
  • Timeouts: 5 min idle, 10 min hard cap. Device codes typically expire inside 15.
  • Daemon restart: the map is lost. The UI already sees a fresh connectorInstanceId on reconnect (protocol.ts:87) and marks outstanding requests expired rather than hanging forever.

Per-provider drivers

A small AuthDriver per provider: the login command, plus matchUrl, matchCodePrompt, matchSuccess, matchFailure against PTY output.

This regex matching is the most fragile part of the design, so it fails open. If no URL matches within about 15 seconds, the daemon streams the sanitized PTY tail to the UI so the operator can read whatever the CLI actually said and still act on it. A brittle matcher degrades to slightly-worse UI, never to a dead end. This single decision is what stops the feature from becoming the next thing you SSH to work around — which would defeat its entire purpose.

On success the daemon immediately re-probes, pushes a fresh hostSnapshot, and releases the circuit breaker. Hygiene: URL and code exist only in transit and in memory, and both are redacted from journald.

04UI surface

Canonical detail lives on the node page (nodes/[machineId]/page.tsx): one card per agent showing the state pill, checkedAt, and the provider's verbatim error. A badge appears on the nodes list and on provider-capacity-cards.tsx, where the operator already looks. The settings page the TODO suggested is dropped — one canonical home.

StateMeaningAction offered
readyProbe passes, no credit latchNone
unauthenticatedAuth probe exited non-zeroSign in — opens the auth flow
no_creditAuthenticated; a real run returned 402 / quotaTop up — links to provider billing. No sign-in button anywhere.
unavailableCLI missing or version probe failedNone — “not installed”

Getting that third row wrong is precisely how an operator loops on the wrong remedy for a week. Mutations are gated on protectedProcedure (trpc.ts:153); Bob has no user roles, and inventing them here would be premature.

Auth modal flow

Click Sign in → spinner while the PTY spawns → the verification URL appears as a link with a copy button and the instruction “open this, then paste your code below” → code input → verifying → the card flips to Ready and the modal closes. Failure at any step shows the provider's own message rather than a generic error, plus the raw PTY tail behind a disclosure.

05The circuit breaker

This conflicts with a deliberate existing decision, and the conflict has to be resolved rather than ignored. agentHealthRouter.ts:8 documents the opposite behaviour on purpose:

“If EVERY agent looks unhealthy the plain rotation is used (a broken runner must not stop dispatch entirely; the starvation alert covers that case).”

That comment is not an oversight and it is not wrong. The reconciliation is what kind of evidence the halt is based on:

  • assessAgentHealth infers unhealth from run statistics. Inference produces false positives, and halting an entire backlog on a statistical artifact is exactly the wedge that comment protects against. Never halt on this.
  • A probe returning unauthenticated, or a latched no_credit from an actual 402, is a confirmed fact. Dispatching into it cannot succeed. Halt on this.

The breaker therefore trips only on hard evidence, and the existing guarantee survives intact. A manual “dispatch anyway” override sits in the banner, so no health bug can ever wedge the operator with no way out — the same failure mode this whole project exists to eliminate.

Concretely: pickAgent() (apps/bob-task-runner/task-runner.js:216) currently logs “No healthy agents” and dispatches anyway. It returns null on confirmed-dead-only, and the claim loop skips rather than churning.

09Verification

The regression that matters most, stated plainly: an authenticated but out-of-credit agent must resolve to no_credit, never to ready. That single assertion pins the eight-day outage.

  • Pure unit, no daemon required: AuthDriver matchers against real CLI output fixtures including failure and expiry text; the no_credit latch state machine; the breaker's evidence classifier — where the load-bearing test is that inference alone never trips it.
  • Protocol: round-trip encode/decode for the four new messages alongside the existing protocol.test.ts, plus a relay test that an auth message reaches only the addressed workspace's daemon.
  • End-to-end acceptance: revoke a token on the host, confirm the UI reports it, re-authenticate entirely from the browser, and confirm dispatch resumes — without opening an SSH session at any point.

10Open questions

  1. Does each provider CLI accept the pasted code on stdin under a PTY, or do any require their own polling flow? Resolve with a Phase 2 spike before the modal is built.
  2. Should no_credit also fire a push notification, or is the dashboard badge plus existing starvation alerting enough? Leaning enough — the TODO's own conclusion is that detection was never the missing piece.
  3. Multi-node: the design is per-node by construction, but if several nodes share one provider account, a single top-up clears all of them. Worth revisiting only when a second agent node exists.

Provenance. This design supersedes the third entry in TODOS.md (added 2026-08-29).
