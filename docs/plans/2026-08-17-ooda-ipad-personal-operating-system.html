Overview

OODA already has durable conversations, resumable streams, policy-visible context packs, bounded agent jobs, proposal approvals, and integration receipts. The missing daily-driver layer is not another kernel rewrite: it is an iPadOS 26 workspace, guaranteed local transcription, trustworthy offline projections, explicit venture scope, Obsidian Git retrieval, and a complete brainstorming-to-approved-work ladder.

This plan delivers a vertical slice first: open OODA on an iPad, speak locally, inspect or correct the transcript, brainstorm with venture and vault context, approve an Obsidian note or task, and inspect the receipt. Later phases deepen portfolio navigation, memory, agent orchestration, operations, and cross-device parity.

Implementation protocol. Execute from isolated worktrees based on current forge/master. Use test-driven development for each package, land small changesets, and re-run the cross-package contract suite at every phase boundary. Never modify the dirty canonical Bob, vault, or KanBanger checkouts.

Current state and proof boundary

  • Production source begins at Bob merge e8e742a9, which unlocked private opportunity reviews without enabling BizPulse writes.
  • The current iPad shell supports Tasks and Planning only; /chat falls back to the Tasks surface.
  • Current speech uses expo-speech-recognition. It requests system on-device recognition when available, but no app-owned transcription engine or model lifecycle exists.
  • Offline accepted turns are durable, but synced transcript history, proposals, corrections, and context are not cached.
  • BizPulse context is live but shallow; venture selection and typed venture-to-project mappings are absent.
  • The Obsidian adapter safely writes approved notes, but personal vault retrieval, Git sync, citations, and a working tablet browser are absent.
  • The planning worktree dependency baseline is Unverified: Node 24 was selected correctly, but the monorepo linker was terminated before package binaries were complete. Phase 0 must establish a clean baseline before source edits.

Goals & non-goals

Goals

  • Make OODA the default iPadOS 26 conversational workspace.
  • Guarantee local microphone transcription by default.
  • Blend permitted Obsidian, BizPulse, Bob, KanBanger, and ForgeGraph evidence with visible provenance.
  • Support existing-venture and new-opportunity brainstorming without silently creating work.
  • Preserve Bob planning and execution capabilities inside both the iPad PersonalOS surface and OODA web.
  • Turn approved outcomes into idempotent, repairable external deliveries.
  • Prove usability on a real iPad through a 14-day dogfood gate.

Non-goals

  • Spoken answers, ambient listening, or wake words.
  • Fully offline LLM inference.
  • Automatic external writes, publishing, purchasing, or destructive actions.
  • Making LangGraph, LangChain, or Strands the OODA kernel.
  • Mirroring every conversation into Obsidian.
  • Multi-user collaboration or Android-tablet parity in the first release.

Required PersonalOS full-loop slice
  1. Start or resume an OODA discussion and approve an opportunity review.
  2. Create or link the canonical BizPulse venture and its typed execution-project mapping.
  3. Create approved KanBanger project/tasks with OODA source-event and proposal lineage.
  4. Open those tasks from the iPad PersonalOS workspace and OODA web; verify Bob’s planning, task-tree, dispatch, live-run, cancellation, retry, artifact, and review controls remain functional.
  5. Execute in Bob and correlate every run, commit, PR or ForgeGraph changeset, check, artifact, build, and deployment receipt.
  6. Let Bob/KanBanger perform their owned completion transition only after acceptance criteria and required deployment evidence pass; otherwise show an explicit close proposal or repair card.
  7. Project the closed task and completed project back into both OODA clients, with a reflection event and deep links to every canonical owner.

The iPad and web clients share contracts and view models, not UI components. OODA never declares a task closed from conversational inference alone, and a successful deployment does not imply acceptance unless the task’s completion policy says it does.

Framework boundary

  execute(input: {

OODA continues to own event sequencing, policy, leases, cancellation fencing, proposal approval, delivery idempotency, and dead letters. LangGraph checkpoints are attempt-scoped and disposable. Strands may be evaluated for disposable API-based workers, not standardized as the kernel.

Cross-phase TDD and commit discipline

Every independently reviewable task follows the same sequence:

  1. Write the smallest failing unit, contract, integration, or device test.
  2. Run it and record the expected failure—not an unrelated setup failure.
  3. Implement only enough behavior to pass.
  4. Run focused tests, package typecheck, and adjacent security/idempotency tests.
  5. Refactor without changing behavior, then re-run.
  6. Create one focused changeset/commit and request independent review before the next risky boundary.

Production acceptance scenarios

  • Existing venture full loop: select a venture, inspect the brief, speak a question, retrieve a relevant note/task/changeset, create an approved task, operate the Bob plan/run/review UI on iPad and web, observe its PR/changeset/build/deployment in ForgeGraph, close the KanBanger task under its completion policy, and follow every receipt back to the originating conversation.
  • New opportunity: begin New thought, speak a multi-minute idea, extract multiple seeds, compare against the portfolio, research uncertainty, edit the opportunity review, and either incubate or approve one BizPulse venture.
  • Personal knowledge: retrieve a permitted vault section with exact citation, approve a new Capture, push one scoped commit, and reconcile the mirror without touching unrelated work.
  • Offline: open cached history, record and edit locally, queue a turn, force-quit, reboot, reconnect, and observe exactly one durable event and response.
  • Privacy: attempt to use a sensitive note with a new provider, deny disclosure, verify the excerpt never appears in request logs/events/analytics, and continue with general context.
  • Failure: kill a provider, runner, source connector, and destination at each commit boundary; show bounded degradation and a repair path without manual database edits.

Rollout order

  1. Shadow contracts, projections, and source freshness only.
  2. Enable the OODA tablet shell for the owner account with text input.
  3. Enable SpeechAnalyzer/model setup and local capture; keep cloud retry off.
  4. Enable encrypted offline transcript projection and Face ID.
  5. Enable read-only venture/task/ForgeGraph and general Obsidian context.
  6. Enable private opportunity reviews and editable proposal drafts.
  7. Enable approved Obsidian writes; then approved Bob/KanBanger writes.
  8. Enable BizPulse venture/mapping writes only after staging idempotency proof and just-in-time credential approval.
  9. Complete the Phase 5 full-loop slice from both iPad and web before enabling broader autonomous jobs or retiring any Bob UI route.
  10. Enable research/scratch/comparison cards and operational control center.
  11. Complete seven-day slice gate, then 14-day replacement dogfood.

Production success gates

  • Zero lost accepted turns, duplicate durable objects, or unauthorized disclosures during 14 days.
  • At least 90% of ordinary voice turns accepted without transcript correction on the target iPad.
  • Airplane-mode capture survives force-quit and reboot and reconciles automatically.
  • Every external write has proposal, exact approved version, idempotency key, receipt, and deep link.
  • At least one existing-venture brainstorm and one new-opportunity review produce useful outcomes.
  • At least one approved Obsidian note and one approved Bob/KanBanger task complete without manual database repair.
  • One project completes OODA discussion → approved BizPulse venture → KanBanger tasks → Bob execution → ForgeGraph PR/changeset/build/deployment → policy-valid closed tasks → OODA reflection from both iPad and web.
  • Every Bob capability used by that slice—planning, task tree, dispatch, live run, cancel/retry, artifacts/diff, review, and evidence navigation—remains functional in PersonalOS or has an intentional deep link with preserved return context.
  • The iPad replaces the current general-purpose chat app for routine daily conversation.

Open questions

No unresolved product decisions. The target is iPadOS 26, local transcription, visual responses, adaptive OODA-first navigation, GitHub-backed Obsidian access, explicit approvals, and canonical system boundaries. The actual iPad model, transcription-engine winner, and final performance numbers are empirical Phase 0/3 findings—not reasons to invent a product decision now.

Execution handoff

Start with Phase 0 in a new isolated implementation worktree. Use the executing-plans workflow task by task. The first review checkpoint is after Phase 2: OODA must be the working default iPad surface with text input before native speech dependencies are introduced. The second is after Phase 4: the real device must prove local capture and offline durability before external context writes are enabled. The third is after Phase 5: both iPad and web must complete the same seeded OODA → BizPulse → KanBanger → Bob → ForgeGraph → deployment → closure loop, including Bob UI parity, before legacy routes are retired or broader automation is enabled.
