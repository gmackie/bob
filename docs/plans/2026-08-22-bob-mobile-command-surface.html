Bob · Mobile · Hermes · OODA

Make Bob the daily mobile command surface

An execution plan for one trustworthy mobile front door: capture and deliberate through OODA, inspect and approve work through Bob, reach Hermes when conversational operations are useful, and preserve explicit authority at every durable boundary.

Status: ready for implementationDate: 2026-08-22Owner: Bob platformHorizon: 8–10 weeks

Executive decision

apps/mobile-bob is the sole production mobile client. OODA remains the deliberation and memory authority, Bob remains the execution authority, Hermes is an operator runtime behind bounded intents, and Skillfleet remains the fleet/configuration authority. The standalone OODA mobile shell becomes a contract fixture and is retired after parity evidence exists.

Why this direction: Bob mobile already has tested conversation streaming, voice state machines, TTS/barge-in, offline outbox, memory and vault browsing, jobs, proposals, corrections, and context inspection. Rebuilding those features in a second app would create two stores, two offline semantics, and two approval surfaces.

Cross-repository contract and delivery protocol

  1. Contract changes start in the owning OODA or Skillfleet repository with failing compatibility fixtures.
  2. Publish a pinned contract artifact and compatibility manifest; do not copy source by hand.
  3. Update Bob’s consumer and golden fixtures in a separate commit.
  4. Run producer current + producer previous, consumer current + consumer previous, and unknown-field rejection.
  5. Deploy server compatibility first, then mobile; keep old mobile supported for at least one release window.
  6. Remove compatibility code only after aggregate version telemetry shows the old client below the agreed threshold.

Definition of done

Functional

  • Today, Capture, Chat, Work, Approvals and Fleet journeys work on iPhone and iPad.
  • Voice, text and offline capture converge on one canonical event stream.
  • Hermes and Skillfleet mutations are proposal-driven.

Safety

  • No transcript, prompt, raw path, account identity or credential in aggregate telemetry.
  • Approval is owner-bound, payload-bound, expiring and single use.
  • Verification failure produces visible rollback evidence.

Reliability

  • 14-day dogfood has no lost accepted capture, duplicate durable object or unauthorized write.
  • Crash, reconnect, notification and device-loss matrices pass.
  • Partial dependencies never create false green state.

Release proof

  • CI, artifact, discovery, install, restart, auth and live runtime are recorded separately.
  • Capability kill switches tested.
  • Standalone OODA mobile retired only after parity gate.

Open questions to close in Phase 0

  1. Which approval consequence classes require biometric step-up versus an authenticated tap?
  2. What is the support window for the previous mobile contract version: 30 or 60 days?
  3. Should Fleet remain under More until weekly usage exceeds a threshold, or become top-level for the initial operator cohort?
  4. Which attachments may be retained in OODA, and which should remain ephemeral until explicit promotion?
Recommended defaults: biometric step-up for deployment, fleet mutation, external communication and credential-adjacent actions; 60-day contract support; Fleet under More; attachments ephemeral until promotion.
