Cross-repository implementation plan · 21 August 2026

One notification plane:
Skillfleet → Bob → Hermes

Replace Skillfleet’s parallel Bob and direct-Telegram adapters with one signed envelope. Bob authenticates and deduplicates it; Hermes owns scheduling, model execution, and Telegram delivery.

Outcome

Fleet insights and urgent alerts arrive through the already-operated Hermes bot without copying Telegram credentials across machines.

Proof boundary

Unit contracts, replay tests, Bob↔Hermes origin canary, and one non-sensitive Telegram canary are reported separately.

Scope

Backend delivery only. No Hermes console port, no notification UI, and no new agent daemon.

What already exists

Skillfleet

A privacy-safe notification schema, record links, and generic transport request builders already exist. Run a five-minute urgent scan and a distinct daily digest trigger so an early snapshot cannot stale the digest; replace channel-specific credentials.

Bob

The production Worker, webhook delivery ledger, Hyperdrive database access, and HMAC verification patterns already exist. Extend those boundaries rather than creating a new service.

Hermes

The dashboard API, rotating session token, one-shot cron jobs, Telegram home target, gateway, and canary timers are live. Hermes remains the sole Telegram credential owner.

Implementation sequence

  1. Harden Bob’s ledger. Add the missing partial unique index for non-null webhook delivery IDs and make the insert conflict-safe.
  2. Build Bob’s pure delivery module test-first. Cover canonical parsing, HMAC/timestamp validation, payload mismatch, pending/processed/failed claims, Hermes token bootstrap, reconciliation, creation, and upstream errors.
  3. Wire the Worker route and origin auth. Keep service credentials server-only and use distinct secrets for Skillfleet ingress and Hermes origin access.
  4. Extend the checked-in nginx contract. Preserve session-authenticated dashboard access and add a narrow service-only API location.
  5. Replace Skillfleet channel adapters. Emit one Hermes/Bob envelope and signed request; separate the five-minute urgent scan from the daily digest trigger; remove direct Telegram bot-token and chat-ID handling.
  6. Prove in layers. Run focused tests, typechecks, full relevant suites, database migration dry-run, origin canary, then one labeled Telegram canary.

Deployment and rollback

  1. Land the Bob migration and code through its normal ForgeGraph PR/CI path.
  2. Install both Worker secrets without printing their values; deploy Bob.
  3. Apply and validate nginx configuration, then reload; keep the prior config recoverable.
  4. Configure Skillfleet with only the Bob endpoint and ingress HMAC secret.
  5. Send a synthetic, non-sensitive canary and verify ledger → Hermes job/run → Telegram independently.
  6. Rollback by disabling the Skillfleet sender, restoring nginx, and reverting Bob; existing Hermes jobs and Telegram configuration remain intact.

NOT in scope

  • Porting the stale Hermes console branch wholesale; it is hundreds of commits behind Bob master.
  • Replacing Hermes’ Telegram adapter or copying its Telegram token into Skillfleet.
  • A new notification UI, preferences model, multi-recipient routing, or generalized public webhook product.
  • Claiming fleet-wide delivery until each actual host is configured and observed; missing hosts remain explicit.
  • Embedding transcript text, raw filesystem paths, prompts, or customer evidence in notification payloads.

Parallelization

Two isolated lanes can proceed after the contract is frozen: Lane A implements Bob ingress/ledger/origin bridging; Lane B updates Skillfleet signing and tests. Live integration and deployment are sequential after both lanes pass.
