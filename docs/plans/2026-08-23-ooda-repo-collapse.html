00Overview

OODA's codebase was mechanically copied into the Bob monorepo in Phase 8A on 2026-04-25. Since then Bob's copy grew a kernel, an oracle, a contracts/v1 layer and nine integration adapters that the standalone ooda repo never received. Production for both products now builds from the Bob monorepo, off one shared Postgres, served by one runner, with one mobile app.

What is left is not a migration — it is a cleanup with a gate in front of it. The standalone repo is ahead of the fold in exactly two files, both live features with real consumers. Port those, prove parity, then retire the surfaces that are quietly lying about being deployable.

The third phase is the part worth keeping from OODA's own convergence plan: the product boundary. It survives the collapse as a package wall — packages/ooda must not import @bob/*, packages/bob must not import @gmacko/ooda, and apps/* is the only place the two compose. That wall is already 99% standing: there is exactly one crossing import in the whole tree.

01Goals & non-goals

Goals

  • Bob's fold becomes a strict superset — nothing in the ooda repo is lost on the way out
  • Parity is proven and committed as evidence before anything is archived
  • No config anywhere claims to deploy a service that no longer exists
  • The Bob/OODA boundary is machine-checked in CI, not a convention
  • One page in CLAUDE.md says who owns what and how durable action crosses

Non-goals

  • Merging the products — that stays a separate decision, downstream of this one
  • Phase 8B schema merge (OODA tables into @gmacko/core/db) — still deferred
  • Phase 8C tRPC → Effect-RPC conversion — untouched
  • Rewriting the host daemon in Go, or in anything — the language question stays open
  • A published cross-repo contracts artifact — the whole point is that there is no second repo to contract with

02Decisions this plan assumes

Each of these is a finding from the 2026-08-23 survey, not an assumption:

#DecisionEvidence
D1 The Bob monorepo is the source of truth for OODA. Work happens in packages/ooda/, not the standalone repo. Kernel, oracle, contracts/v1, integrations exist only in Bob. agent-adapters 8×, db 2.6×, api 1.9× ahead.
D2 The boundary is a package wall, not a repo wall. Enforced by a CI guard in the existing node --test style. Exactly one crossing import exists today: packages/ooda/src/oracle/embeddings.ts → @bob/telemetry. Zero in the other direction.
D3 The ghost deployment is retired before the repo is archived, not after. The ooda repo still ships a production stack for ooda.gmac.io, which is now served by the Bob repo's edge worker off Bob's database.
D4 bob-cli is retired, the language question is not. Archive the Go repo; re-evaluate Go vs Node separately. Confirmed by Graham. Dormant since 2026-05-07; absent from the live path.
D5 Parity is proven before archiving — OODA's own Phase 0.2 semantic diff, run once, at the right moment. That census was the good idea in the competing plan. It just belongs at the exit, not as the foundation of a six-week two-repo programme.

Why the journal port is safe

emitSkillfleetWorkflowEvent returns {state: "disabled"} and touches nothing when no journal path is configured, via option or env. Porting it is a strict no-op on the running system until someone deliberately sets the path — which is also what makes 1.2 landable ahead of any Skillfleet-side decision.

What about @ooda/ui?

@gmacko/core/ui is a strict superset of the standalone @ooda/ui — it has every component (button, dropdown-menu, field, input, label, separator, toast, theme) plus roughly fifteen more. The only file without a counterpart is button.stories.tsx. Port it if a Storybook setup exists in the monorepo; otherwise record it as an intentional drop in the parity report rather than leaving it unclassified.

03Risks & mitigations

RiskRatingMitigation / stop condition
Someone deploys the retired app definition over the live domain High impact, low odds Task 2.1 runs first and deletes every copy of the definition. Stop condition: if the app record cannot be retired, do not archive the repo — a readable repo with a live record is safer than a hidden one.
The parity census misses runtime-only divergence — migrations, env vars, systemd units, seed data Medium A symbol census sees exports, not configuration. Task 1.5 explicitly pairs it with a hand-diff of migrations and .env.example. If either shows drift, it becomes a task before the gate closes.
Someone else is working in the standalone repo Unknown — see open questions Phase 2 is blocked on this answer, Phase 1 and 3 are not. If the answer is yes, Phase 1 still lands (it only adds), and the archive becomes a coordination step rather than a mechanical one.
Journal wiring changes runner behavior Low Disabled unless a journal path is configured; a test asserts the disabled path. Land 1.1 and 1.2 separately so a revert is one commit.
Sweeping empty directories breaks a stale project reference Low Serial typecheck across the workspace catches dangling tsconfig references; do 2.5 last in its phase so it is trivially revertible.
The boundary guard becomes a rubber stamp — someone adds an allowlist entry instead of fixing the import Medium, long-term Keep the guard allowlist-free. There is exactly one crossing today and 3.1 removes it, so the correct state is zero exceptions — any proposed exception is a design conversation, not a config edit.

05Open questions

  • Is anyone else working in the standalone repo? The April note said the OODA work was happening in parallel. This gates Phase 2 and nothing else — worth answering before starting, cheap to answer.
  • Go or Node for the host daemon? Node won by accretion: the gateway client grew inside the runner because the adapters, job protocol and contracts were already there, and splitting it out means maintaining the session protocol twice. Go buys a single static binary with no runtime dependency — which only matters if the daemon ships to other people's machines. That makes it downstream of the multi-tenancy question, not an independent call.
  • Does the public multi-tenant platform change the packaging answer? If OODA is meant to ship as a tenant-facing product rather than an internal tool, the packaging question is different — and it is the same question that decides the one above.
  • Does the OODA schema stay separate inside the shared database? Phase 8B (merging OODA's tables into the core schema with tenant FKs) was planned in April and never landed. It is out of scope here, but leaving it undecided indefinitely is how the next fold starts.
