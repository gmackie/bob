Recommendation. Ship three phases in order, each as its own PR that lands on master and is verified in production before the next one starts.
  1. Phase 2: a command channel from the SdlcEdge back to the coordinator, carried on the exporter's existing outbound requests, with tiers and a named human actor. Plus web actions and an Ink TUI.
  2. Phase 3: make waiting-input real. A tail relay next to the coordinator follows each running attempt's t3 thread, reports pending questions to the coordinator, and streams a short live tail to the edge. Answers go through ResolveInput.
  3. Phase 4: a mobile Attention tab with push and confirmation sheets, and a bob_sdlc view in the t3code plugin.
The coordinator stays the only writer, and it still never opens an inbound port.

Goals and non-goals

Goals

  • Run tier 1–2 commands from web, TUI and mobile, with confirmation and an audit of who did what
  • Make waiting-input a real state, answerable from any surface
  • Live attempt tail and display-only CI phases at L5
  • Push alerts on new waiting-input, review gates and failures
  • Show the item behind the current t3 thread inside t3code

Non-goals (separate issues)

  • Implementing release, validation and deployment execution in the coordinator. Those buttons follow GetCapabilities and stay disabled with a reason until a coordinator track ships them.
  • Moving the legacy loop onto plans
  • Upgrading Bob's Effect to 4.1.3
  • New native modules in mobile-bob. Phase 4 has to ship as an over-the-air (EAS) update.

Key decisions

Commands ride the exporter's outbound POST

The DO queues commands in an outbox, and each ingest response returns them. While anything is pending, or a client is connected, the exporter polls every 2 s, so a command reaches the coordinator in about 2 s. Otherwise it keeps the 30 s heartbeat. Results come back in the next batch. No inbound port, no second socket.

One edge principal, a named actor per command

The exporter runs commands in-process under a dedicated edge principal context with its own operation allowlist. Each command also carries actor (the Bob user id the DO verified), which is recorded in a new coordination_command_log. That's simpler than one coordinator principal per human, and the principal policy still applies on top.

Native clients use device-login API keys

/api/sdlc/ws also accepts Authorization: Bearer bob_…, minted by the existing device flow (/api/v1/device/*), when no Origin header is sent. Browsers keep the session and same-origin check. Both still go through SDLC_VIEWER_USER_IDS.

Bob writes a small t3 client

No reusable Node client exists yet. runtime/t3-client.mjs speaks just enough of t3's websocket RPC (subscribeThread, subscribeShell, dispatchCommand with runtime-request.respond), pinned by contract tests on recorded frames. If t3code ships its facade, we swap it in.

Mitigations
  • R1 public command surface: the viewer allow-list, tiers, typed confirmation for tier 3, the coordinator's principal allowlist for the edge principal, and per-command actor logging. Release and deploy operations stay disabled until a later track.
  • R2 duplicate effects: commandId is the coordinator's idempotency key, and a replay returns the stored receipt. The outbox is drained with acknowledgements; delivery is at least once, the effect happens once.
  • R3 t3 protocol drift: the relay's client sits behind a small interface, pinned by recorded-frame tests. If the relay fails, the UI shows “live detail unavailable” and state is unaffected.
  • R4 push noise: deduplicated per item, state and version, with a per-type preference toggle; only viewers on the allow-list get pushes.
  • R5 polling cost: 2 s polling only while commands are pending or clients are connected; idle stays at the 30 s heartbeat.
  • R6 Ink layout: the DAG is drawn as an indented tree, with OpenTUI as a fallback.
  • R7 production enum migration: additive ADD VALUE only, applied as postgres over SSH like 0041, before the Worker deploys.

Verification and delivery

  • Each phase is one PR on gmackie/bob (Phase 4 adds one on t3code-bob-plugin). It's approved only when every check is green on its exact head, then merged.
  • Production per phase: the Worker deploy through CI, checked against wrangler deployments; a new coordinator release on hetzner-bob that passes host verification, with the previous release and unit file kept for rollback (as in Phase 1).
  • Production evidence uses the BOB-75 pilot plan: Phase 2 pause and resume from the web and the TUI; Phase 3 a pilot attempt that asks a question answered from the TUI; Phase 4 the same from the simulator, plus the plugin view on the pilot thread.
  • Kanbanger: one child issue per phase under BOB-75, kept open until production is verified; BOB-75 closes after Phase 4.
