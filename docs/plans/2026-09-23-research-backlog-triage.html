Overview

The hetzner-bob workspace holds 4,424 work items. 3,783 of them — 85% — have no project attached, were all created between 2 and 22 September, and carry titles averaging 236 characters. They are machine-generated research hypotheses about Gaussian splatting, defect detection and synthetic data generation.

The remaining 641 items belong to real projects (BOB, BizPulse, HabitPlay, LevelForge, ForgeGraph and others). Those are in good shape: 23 of BOB's 78 items are done, 20 of BizPulse's 52, and almost none are stuck. The problem is entirely in the generated cohort.

The core defect

More than half of all runs failed outright. Of the 3,171 that completed, 3,051 finished without attaching any artifact — and the work item was still advanced to in_review. So "Review ready" is being asserted on the basis of a run terminating, not on the basis of a run producing something reviewable.

Why they are not completing

Three independent failures stack up, and each one alone would be enough to stall the pipeline.

1. Runs fail more often than they succeed

3,458 failures against 3,171 completions. Nothing downstream can work while the majority of attempts die. The one item carrying a diagnostic says it plainly: 3 runs died without finishing; last: session d606258b (claude) reaped as stuck.

2. Completion does not mean output

96% of completed runs attached nothing. Whatever the agent did, it left no artifact, no comment and no diff reference on the item. From Bob's point of view the run succeeded and the item became reviewable, which is how 3,116 empty reviews accumulated.

3. Status is never reconciled

454 items say in progress while zero runs are live; 275 of those never had a run at all. Nothing moves an item back when its run dies or never starts. The status is a claim made at dispatch that is never retracted.

Compounding: duplicates and unreadable titles

288 titles appear more than once, covering 578 items — the pipeline regenerates the same hypothesis. And because the title field carries the whole hypothesis paragraph (236 characters, with markdown backticks), every list and detail screen is unreadable. That is a display bug, but it is why the backlog feels worse than it is.

Are they needed?

Mostly no, in their current form. The evidence:

  • No provenance. 3,299 have empty source_metadata; the rest carry only {"attempts": n}. Nothing records which experiment or run produced them.
  • No project. They are not attached to any project, so they do not roll up anywhere and cannot be prioritised against real work.
  • No output. 3,116 of them have produced literally nothing across 6,641 runs.
  • Regenerable. They are derived hypotheses. If the generator still has its inputs, the useful ones can be recreated with provenance attached.

The ~131 runs that did produce artifacts are the exception worth preserving before any bulk action.

On KanBanger

There is no KanBanger linkage on any of these. external_provider across the whole workspace is only linear (586 items, the healthy real projects) and ooda (1). The generated cohort has no external provider at all. So there are no related KanBanger tasks to reconcile — the integration simply is not involved here.

Phase 3 — Land the backlog

Three options. They are not mutually exclusive: the recommendation is C for the empty reviews and B for the stalled in-progress items.

A. Re-run them

Dispatch the 3,116 empty reviews again. Not recommended. At the observed 52% failure rate and 4% artifact rate this burns roughly 6,000 agent runs to produce perhaps 120 artifacts, and the underlying "completed but empty" defect is unfixed, so most would land back in the same state.

B. Reconcile status honestly Recommended for in_progress

Move the 454 in-progress items to a status that matches reality: todo where no run exists (275 items), failed where the last run failed. This is what a reaper should have done. It makes the board truthful without discarding anything.

C. Close the empty reviews Recommended for in_review

Cancel the 3,116 in-review items that have no artifact, no comment and no successful-with-output run. They are asking for a review that cannot be performed. Keep the ~120 with artifacts open for actual review. This is reversible: status change only, nothing deleted.

Approval required

Phase 3 rewrites thousands of production rows. I will not run any of it without an explicit go, and I would do it in a transaction with a recorded before/after count, in batches, starting with a dry run that reports exactly which ids would change.
