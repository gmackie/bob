Bob · Agent Execution

Checklist-Driven Agent Execution Plans become first-class checklists. Bob walks them item-by-item, gates each, reviews, ships, and takes feedback.

Draft Design validated
2026-08-14 · gmackie/bob @ feat/checklist-execution · design by Graham + Claude

Turn the agent loop from "one shot per issue" into a plan-driven, gated pipeline: an agent's plan is materialized as an ordered checklist of first-class tasks; Bob's server walks it one item at a time, verifies each item's gate (never letting the agent self-certify), reprompts to keep going, then opens a PR, reviews it, holds for third-party review, and folds their feedback back in as repair loops until merged.

Goals & Non-goals

Goals

  • Plans → first-class ordered checklists with per-item gates.
  • Bob's server walks the checklist item-by-item; agents are reprompted to continue, never self-advance.
  • Every item passes a gate (outcome-verified, not self-reported) before the next starts.
  • Bob opens the PR, self-reviews, holds for third-party review, ingests human feedback as repair loops.
  • BizPulse/Kanbanger tasks flow through this rich path.

Non-goals (for now)

  • Rewriting task-runner.js — it stays as a bridge/fallback.
  • New VCS host integration — reuse existing forge/github provider clients.
  • Replacing the ws-gateway/daemon execution path — we drive it, not rebuild it.
  • Autonomous merge without gates — merge stays gated (CI + approval).

What already exists reuse

Design against these; don't reinvent them.

Checklist / task models

planTaskItems (ordered, nestable, pending/in_progress/completed/cancelled) · requirements (checkable, pending/in_progress/done, has UI) · dispatchItems (blockedByItems DAG + sortOrder + pipelineState).

Orchestration drivers

Cron-driven on the bob worker: autoDrainBacklog (dispatch next), dispatchCheckProgress (advance items as gates clear), autoReviewAndMerge.

Execution path

executeTask → ws-gateway nudge → daemon. Sessions = chatConversations (workflowStatus, awaitingInput*), runs = taskRuns.runPhase = shape/plan/execute/review/ship.

Review / PR / feedback

autoReviewAndMerge: reviewer-bot posts native git-host review → dispatchRepairSession on changes_requested → merge on approval+CI. pullRequests, prReviews, forgeRevisions.gates.

Risks & Mitigations

Agent self-advances anyway. A capable agent may ignore "edit only, don't touch git / don't self-complete" (codex opened its own PR on GMA-412). Mitigation: the server is the sole authority — it detects working-tree changes, runs the gate, and marks completion; the agent's self-report is never trusted. Gate failure reprompts the same item.
Cost / latency of per-item dispatch. Fresh context per item multiplies agent runs. Mitigation: allow "batch" items where cheap; concurrency + daily caps already exist in autoDrainBacklog; deterministic gates avoid extra reviewer-agent calls.
Two execution systems drift. Building on the server path while task-runner.js still runs. Mitigation: Phase 4 makes the server path authoritative for synced issues; the legacy runner is fallback only.
Forge vs GitHub PR routing. The runner pushes to forge; codex opened a GitHub PR. Mitigation: standardize PR target via the existing provider clients / gitProviderConnections per repo before Phase 3.

Verification

  • P1: a work item with a 3-item checklist executes in order; a deliberately-failing gate blocks only its item and reprompts; UI shows live progress.
  • P2: a planning session produces a gated checklist; a subjective item passes only on independent reviewer-bot approval.
  • P3: a completed checklist opens a PR; a human "changes requested" (incl. inline) triggers a repair push and re-request; approval → merge.
  • P4: one real BizPulse/Kanbanger task lands via the full path, replacing the legacy runner for that issue.

Open questions

  1. Should planTaskItems be the canonical checklist, or do we fold requirements into it? (Lean: planTaskItems for execution, keep requirements as the human-facing view over it.)
  2. Default gate when the plan doesn't specify one — build+ci, or require the planner to always author a gate?
  3. Which repos require external human approval by default vs. bot-approve+merge? (Per-repo policy in gitProviderConnections?)
  4. Does a Kanbanger↔work-item bridge already partially exist via the ForgeGraph integration, or is it net-new? (Verify at start of P4.)

Sequencing: P1 is load-bearing and self-contained (build + verify first). P2–P3 layer on. P4 connects to the live BizPulse pipeline last, once the rich path is proven on Bob's own work items.
